# Замена ресурсов: учебник по коду редактора

Учебный разбор на русском, собранный из обсуждения и сверенный с кодом 22 сентября 2026 года.
Область разбора — функция `resourceReplacement`, от публичной настройки до CodeMirror
и ProseMirror. Тестовые файлы не рассматриваются. При подготовке учебника тесты не запускались.

Это связное изложение, а не дословная стенограмма: повторные объяснения объединены,
ошибочные ответы исправлены, ссылки обновлены после переносов файлов.
Фрагменты кода местами сокращены; полная реализация доступна по ссылкам.

Согласованные требования находятся в [codex.md](./codex.md). Подробный локальный разбор
сбора и замены Markdown-ресурсов также есть в
[codemirror/resources.md](./packages/editor/src/modules/resource-replacement/codemirror/resources.md).

**Статус изучения:** основная цепочка обоих режимов разобрана. В истории CodeMirror
изучены назначение, отметки вставок и начало обхода событий. Подробный разбор вычислений
`mapEvent`, композиции исправленного undo и установки состояния истории был отложен
по просьбе пользователя. В главе об истории эта граница отмечена явно.

## 1. Задача и правила

Пользователь вставляет содержимое с уже готовыми адресами ресурсов. Приложение может
скопировать соответствующие файлы и вернуть новые адреса. Редактор отвечает за обнаружение
ресурсов, ожидание ответа и применение замен. Само копирование выполняет приложение в `resolve`.

```md
![Схема](/source/a.png)
```

Пример ответа приложения:

```ts
{
    replacements: [
        {kind: 'picture', oldPath: '/source/a.png', newPath: '/target/a.png'},
    ],
}
```

Основные правила:

- Ресурсы включаются явно в `resources`; обычная ссылка сама по себе ресурсом не является.
- Операция запускается на разрешённые `paste` и `drop`. Shift сам по себе не исключает вставку.
- Загрузка бинарного файла из проводника — отдельный механизм.
- Ресурсы внутри кода исключаются как из запроса, так и из применения результата.
- Для одной вставки выполняется один `resolve`; разные вставки могут обрабатываться параллельно.
- В запросе повторы объединяются по `(kind, path)`.
- Результат применяется ко всем текущим совпадениям `(kind, path)` в документе.
- Пока идёт запрос, защищены и показаны с лоадерами только ресурсы исходной вставки.
- Undo/redo и переключение режима блокируются на время незавершённых операций.
- Исходные адреса уже находятся в документе. Сохранение во время ожидания может записать их.
- Пустой или частичный результат — успех. Ошибка и отмена сохраняют исходное содержимое,
  снимают лоадеры и блокировки. Автоматического повтора нет.
- Таймаут необязателен. Если задан, он должен быть конечным положительным числом.
- Поздний ответ завершённой операции не применяется.

Не путать три сущности:

```text
Вхождение — конкретная картинка в определённом месте документа.
Ресурс — пара категории и адреса, например ('picture', '/a.png').
Операция — отдельный вызов resolve со своим operationId.
```

Две картинки с одинаковым адресом — два вхождения, но один ресурс в запросе одной операции.
Повторная вставка такого адреса создаёт новую операцию: постоянного кэша результатов нет.

## 3. Точка входа и владелец операции

### 3.1. Публичная настройка

Упрощённый пример конфигурации с учебным ответом вместо сетевого запроса:

```ts
useMarkdownEditor({
    resourceReplacement: {
        resources: {
            image: {
                kind: 'picture',
                urlAttribute: 'src',
                nameAttribute: 'alt',
            },
        },
        triggers: ['paste', 'drop'],
        resolve: async (resources, {operationId, signal}) => ({
            replacements: resources.map((resource) => ({
                kind: resource.kind,
                oldPath: resource.path,
                newPath: '/copied/a.png',
            })),
        }),
    },
});
```

`image` — имя типа узла. `picture` — категория, выбранная приложением.
Они не обязаны совпадать. `urlAttribute` и `nameAttribute` указывают, какие атрибуты
читать. Без `nameAttribute` имя не добавится в ресурс, даже если у узла есть подпись.

`ResourceTrigger` допускает и строку `'paste'`, и объект `{name: 'paste'}`.
`isResourceTriggerEnabled` приводит оба варианта к имени и проверяет включение.

### 3.2. useMarkdownEditor

Хук собирает расширения WYSIWYG и создаёт `EditorImpl` внутри `useMemo`.
Настройка попадает в него через `...props`. Пересоздание определяется переданным
массивом зависимостей `deps`; это важно при изменении конфигурации извне.
Очистка эффекта отписывает обработчики и вызывает `editor.destroy()`.

### 3.3. EditorImpl

Один экземпляр редактора владеет одним общим контроллером. Контроллер создаётся,
если задан `resolve` и есть хотя бы один включённый тип в `resources`.
Для подключения интеграций дополнительно нужен непустой `triggers`.

Поэтому возможна ситуация: контроллер есть, но вставки ничего не запускают,
потому что интеграции не подключены.

Движки создаются лениво через соответствующие getter. При создании ProseMirror:

1. Регистрируются расширения редактора.
2. Проверяется, что перечисленные в настройке имена узлов существуют.
3. Для всех NodeSpec выставляется `_resource` по конфигурации; у остальных поле очищается.
4. Подключается интеграция замены.

`_resource` хранится в описании типа узла, а не как атрибут каждого экземпляра в документе.
Это метаданные вида «для image читать src и alt», а не флаг ожидания конкретной картинки.
В CodeMirror такого документа узлов нет: туда напрямую передаётся `resources`, а данные
из Markdown извлекают зарегистрированные обработчики.

### 3.4. Почему пользовательский onChange не управляет переключателем

У контроллера два отдельных уведомления:

```text
Внутренний onUpdate → rerender / rerender-toolbar → обновление интерфейса.
Пользовательский onChange → событие о состоянии операции для приложения.
```

`MarkdownEditorView` вычисляет `modeDisabled` по списку незавершённых операций.
Удаление пользовательского `onChange` не отключает внутреннее обновление.
Ошибки этих callback обрабатываются отдельно, чтобы один не мешал другому.

Одной disabled-кнопки недостаточно: `changeEditorMode` может быть вызван программно.
Метод проверяет занятость контроллера и временное состояние движка. Второе закрывает
промежуток между принятой вставкой и запуском запроса в view update.
Проверка повторяется после callback `beforeEditorModeChange`: тот мог синхронно
запустить новую операцию.

При уничтожении сначала отменяются операции контроллера, затем уничтожаются движки.

## 4. Контроллер: от start до finish

### 4.1. Контроллер не знает устройство документов

В `start` движок передаёт подготовленный запрос:

```ts
type ResourceReplacementRequest = {
    resources: readonly ReplacementResource[];
    apply: (replacements: ReadonlyMap<string, string>) => void;
    release: () => void;
};
```

Контроллер решает, когда вызвать `resolve`, применить ответ и завершить ожидание.
Как изменить документ и убрать диапазоны, знают замыкания `apply` и `release`.

### 4.2. Дедупликация и имя

Ключ ресурса вычисляется в `controller.utils.ts`:

```ts
JSON.stringify([resource.kind, resource.path])
```

Имя в ключ не входит. Для двух ресурсов:

```ts
{kind: 'picture', path: '/a.png', name: 'Первая'}
{kind: 'picture', path: '/a.png', name: 'Вторая'}
```

в запрос попадёт первый объект. Имя полезно приложению как подпись, но не определяет,
какой файл копировать. Если у первого объекта имени нет, имя второго не подставляется.

При этом лоадеры не строятся из дедуплицированного списка контроллера. У CodeMirror
данные хранятся при каждом диапазоне, а ProseMirror читает их у каждого узла.
Поэтому два одинаковых адреса могут показывать разные подписи лоадеров.

### 4.3. Последовательность start

1. Отказ, если контроллер уничтожен, нет resolve или список ресурсов пуст.
2. Объединение повторов внутри этой операции.
3. Создание `operationId`, `AbortController` и записи в `pending`.
4. Создание таймера, только если задан `timeoutMs`.
5. Уведомление `pending`.
6. Проверка, что callback уведомления не успел отменить операцию.
7. Запуск асинхронного resolve.

`start` возвращает boolean, а не Promise результата. `true` означает, что операция
была заведена; это не обещание успешной замены. Если `start` вернул `false`, адаптер
сам освобождает уже подготовленную группу диапазонов.

Каждая вставка вызывает новый `start`. Одинаковые адреса в разных операциях не объединяются.
Если конкурентные ответы заменяют один старый адрес по-разному, первый применённый
ответ может убрать совпадения для второго. Дополнительной координации первой версии нет.

### 4.4. Проверка ответа

В resolve передаются копии объектов ресурсов, защищённые `Object.freeze`, и контекст
`{operationId, signal}`. После await сначала проверяется, что операция всё ещё та же
запись в `pending` и контроллер не уничтожен.

`validateReplacements` проверяет структуру результата до применения:

- `replacements` должен быть массивом;
- обязательные поля должны иметь подходящие строковые значения;
- каждая пара `(kind, oldPath)` должна принадлежать запросу;
- повторяющиеся записи для одной пары не должны конфликтовать по `newPath`.

Неизвестная пара или конфликт вызывает ошибку всей операции. Проверка допустимости
самого нового URL выполняется дальше, при подготовке изменений движком.
Пустой массив допустим. Текущий код вызывает `apply` и для пустой карты; адаптер
не создаёт изменений, а операция завершается успехом. Не следует принимать учебную
пометку-комментарий «не вызывать apply» за уже реализованное условие.

### 4.5. finish и освобождение

`finish` первым делом сравнивает запись в `pending` с объектом операции. Если её уже
нет или она другая, повторного завершения не происходит.

Затем очищается таймер, операция удаляется из pending, вызывается release и отправляется
финальный статус. Для ошибки или отмены также вызывается abort.
Ссылки на prepared заменяются пустыми функциями: даже если внешний resolve игнорирует
AbortSignal и долго не завершается, он не должен удерживать через операцию замыкания движка.

`release` нужен и без изменения документа: например, при пустом ответе, отмене или ошибке.
Ошибка в освобождении сообщается через reportError, но не возвращает операцию в pending.

`busy` означает `pending.size > 0`. После завершения операция в pending отсутствует;
история её статусов внутри контроллера не накапливается.

## 5. Интеграции paste/drop

### 5.1. Зачем отдельный слой

Основная реализация движка работает с транзакциями. Интеграция знает о DOM-событиях,
буфере обмена, файлах и настройке paste/drop. Она передаёт чистую функцию `shouldTrack`.
Благодаря этому сетевой вызов не смешан с распознаванием DOM-события.

Регистрация обработчика ресурса не включает операции сама по себе. Для этого нужны
описание типа в resources, разрешённый триггер и resolve.

### 5.2. Замыкание captureSource

В каждой интеграции есть локальный `transferContext`. Функция `captureSource` находится
внутри фабрики интеграции и меняет именно эту переменную. У разных экземпляров редактора
контексты независимы.

Если вынести функцию и передавать переменную аргументом, присваивание параметру нового
объекта не изменит внешнюю переменную. Поэтому во время обсуждения captureSource
оставили внутри интеграций.

```ts
const context = {trigger, /* дополнительные признаки */};
transferContext = context;
queueMicrotask(() => {
    if (transferContext === context) transferContext = undefined;
});
```

Микрозадача убирает краткоживущий контекст после синхронной обработки события.
Сравнение по ссылке не позволяет старой микрозадаче стереть более новый контекст.
Это не таймер ожидания resolve: контекст нужен лишь при связывании события и транзакции.
При blur контекст также очищается, чтобы после потери фокуса не использовать устаревшие
сведения о вставке.

Возврат `false` из DOM-обработчика означает, что интеграция не забирает событие себе.
Она записала источник и позволяет обычным обработчикам редактора выполнить вставку.
Это не тот же смысл, что `false` из filterTransaction.

### 5.3. CodeMirror: массив расширений и приоритет

`createCodeMirrorResourceIntegration` возвращает массив Extension CodeMirror:
обработчики DOM, updateListener и основное расширение замены. Массив — форма композиции
настроек редактора, а не список последовательно выполняемых команд.

`Prec.highest` даёт обработчику высокий приоритет в соответствующем механизме CodeMirror.
Он не превращает DOM handler, transactionExtender и updateListener в одну общую очередь:
они срабатывают на разных стадиях обновления.

Контекст содержит trigger и `plain`. Последний выставляется для вставки в код или
при наличии бинарных файлов в DataTransfer. Название не означает, что любая вставка
через Shift обязательно исключается.

Для drop берётся позиция мыши, а не текущее выделение. Ресурс может быть перетащен
далеко от курсора. shouldTrack также читает userEvent транзакции:
`input.paste`, `input.drop`, `move.drop`.

UpdateListener очищает контекст только при `update.docChanged`. Во время обработки
события возможна промежуточная транзакция с изменением лишь выделения; она не должна
раньше времени уничтожить контекст для следующей транзакции вставки. Это не утверждение,
что каждая стандартная вставка обязана создавать такую промежуточную транзакцию.
Если документ так и не изменился, остаётся очистка микрозадачей.

### 5.4. ProseMirror: перенос контекста в транзакцию

Интеграция создаёт собственный `sourceMeta = new PluginKey(...)`. Ранний плагин
в filterTransaction прикрепляет подходящий transferContext к транзакции:

```ts
tr.setMeta(sourceMeta, transferContext);
transferContext = undefined;
return true;
```

Теперь shouldTrack читает данные из самой транзакции. Они не исчезнут, когда внешнее
замыкание очистится. Признак files исключает отдельный механизм загрузки файлов.
Метаданные uiEvent/paste позволяют сопоставить контекст с типом события;
appendedTransaction не должна повторно захватывать исходный контекст.

`filterTransaction` решает, можно ли принять транзакцию: false отклоняет её, true
позволяет продолжить проверки. В этом раннем плагине оно заодно фиксирует источник;
основная защита ресурсов находится в другом плагине.

`builder.addPlugin` регистрирует конкретный плагин ProseMirror.
`builder.use(ResourceReplacement, options)` запускает расширение нашего редактора,
которое само может проверять схему и регистрировать плагины. Это разные уровни API.

Выделить захват источника в общий самостоятельный плагин возможно в обоих движках,
но в обсуждении решили пока не делать отдельную абстракцию без других потребителей.

<a id="prosemirror"></a>
## 6. ProseMirror: сбор, защита и применение

### 6.1. extension.ts, types.ts и const.ts

`ResourceReplacement` проверяет `_resource` каждого типа узла: должны существовать
kind, urlAttribute и объявление соответствующего атрибута в NodeSpec. Проверка делается
через overrideNodeSpec, чтобы работать с итоговым описанием после настройки расширений.
Затем регистрируется плагин с низким приоритетом.

Состояние плагина — группы диапазонов:

```ts
type ResourceBatch = {
    id: string;
    ranges: {from: number; to: number}[];
    started: boolean;
};
type ResourceReplacementMeta = {
    type: 'start' | 'release';
    id: string;
};
```

`batch.id` связывает записи внутри движка. Это не публичный `operationId` контроллера.
Связь между ними обеспечивают замыкания, переданные при запуске операции.

`const.ts` содержит ключ состояния плагина, метку служебной замены, метку удалённой
транзакции и ключ стандартной истории. Проверка истории ProseMirror читает метаданные
по её ключу, а не CodeMirror userEvent.

### 6.2. isTracked: какую транзакцию рассматривать

Кандидат должен быть исходным локальным изменением документа. Исключаются:
служебная замена, история, appendedTransaction, rebased и помеченные удалённые изменения.
Затем учитываются кодовый контекст и shouldTrack интеграции.

Для drop старое выделение не используется как место вставки. Курсор мог находиться
в коде, а мышь — в обычном абзаце. Проверка фактически вставленных узлов всё равно
исключит код при их сборе.

### 6.3. Откуда берутся несколько диапазонов

Транзакция ProseMirror состоит из шагов. Каждый StepMap описывает координаты до и
после своего шага. Чтобы получить позиции в итоговом документе, новый диапазон шага
проводится через последующие карты:

```ts
const rest = tr.mapping.slice(index + 1);
ranges.push({from: rest.map(from, 1), to: rest.map(to, -1)});
```

Это делает `collectAddedRangesInFinalDocument`. Даже одно пользовательское действие
может состоять из нескольких шагов и добавлений. Поэтому API работает с массивом,
а не предполагает единственный диапазон текущего выделения.

`collectResourcesInRanges` обходит узлы в этих диапазонах, исключает code-узлы и
code-марки, читает `_resource`, проверяет строковый атрибут адреса и полное включение узла.
Результаты складываются в Map по позиции `from`: это убирает повторное чтение одного
вхождения при пересечении диапазонов, но сохраняет разные картинки с одинаковым URL.

### 6.4. state.apply и старт запроса

При каждой подходящей транзакции состояние:

1. Перемещает ранее сохранённые диапазоны через tr.mapping.
2. Удаляет схлопнувшиеся диапазоны.
3. Обрабатывает start/release из метаданных.
4. При новой отслеживаемой вставке добавляет группу `started: false`.

Без изменения документа и без метаданных возвращается прежнее состояние.
Запрос здесь не запускается: вычисление состояния может происходить до окончательного
принятия обновления.

`view.update` находит группы `started: false`, читает ресурсы и сначала отправляет:

```ts
view.dispatch(
    closeHistory(view.state.tr).setMeta(resourceReplacementKey, {
        type: 'start',
        id: batch.id,
    }),
);
```

Именно здесь к транзакции прикрепляется `type: 'start'`. Состояние плагина превращает
его в `started: true`. Метка ставится до controller.start, потому что callbacks
могут синхронно вызвать новую транзакцию и повторный view.update.

### 6.5. filterTransaction и защита

Порядок основных проверок:

```ts
if (tr.getMeta(resolvedResourceMeta)) return true;
if ((controller.busy || batches.length) && isHistoryTransaction(tr)) return false;
if (!tr.docChanged) return true;
if (changesProtectedResources(tr, state, batches)) return false;
```

Служебной замене разрешено менять защищённые ресурсы. Обычные изменения проверяются
по диапазонам уже запущенных групп.

В `changesProtectedResources` есть две проверки для каждого шага:

- Изменённый участок пересекается с защищённым диапазоном?
- Защищённый узел после шага отличается от прежнего?

Вторая нужна для изменения атрибутов и марок: оно может не давать обычного изменённого
текстового диапазона. После каждого шага координаты перемещаются для проверки следующего.

Общий `overlaps` считает вставку в точку пересечением только строго внутри диапазона.
Ввод ровно перед ресурсом или после него не должен блокироваться как изменение ресурса.
Удаление или замена непустого участка проверяется обычным пересечением интервалов.

`closeHistory` на вставке и на последующем start разделяет вставку с соседними действиями.
Он не очищает историю и не создаёт видимое пустое действие undo. Его задача — не дать
соседнему вводу слиться со вставкой в одну историческую группу.

### 6.6. Декорации и размеры

`collectResourceDecorations` заново читает ресурсы в диапазонах и создаёт две декорации:

- node decoration скрывает исходное представление (`display: none`);
- widget decoration показывает индикатор в начале узла.

Сам узел документа не заменяется на лоадер. Для изображения размер индикатора оценивается
по DOM, атрибутам и естественным размерам картинки. Есть запасные размеры, ограничение
шириной редактора и высотой 700. Масштаб не увеличивает изображение сверх исходной оценки.
Для других типов используется текстовый индикатор.

В standalone-редакторе ReactRenderer может отсутствовать; предусмотрен текстовый вариант.
При уничтожении декорации освобождается связанный React-элемент.

### 6.7. Применение ответа и release

`resourceReplacementTransaction` сначала проверяет все новые адреса правилами парсера
текущего ProseMirror. Затем обходит текущий документ целиком, исключает код и сопоставляет
`(kind, path)`. Меняется только указанный атрибут через `setNodeAttribute`.

Обход идёт по исходному для этой транзакции документу, поэтому внутри одного ответа
нет каскада `/a → /b → /c`. Транзакция получает `addToHistory: false` и resolvedResourceMeta.
Если изменений нет, возвращается null.

Адаптер проверяет, что редактор жив и доступен для редактирования, отправляет транзакцию
и сравнивает фактический документ с ожидаемым. При отказе выбрасывает ошибку контроллеру.

Освобождение отправляет отдельную транзакцию:

```ts
view.state.tr
    .setMeta(resourceReplacementKey, {type: 'release', id})
    .setMeta('addToHistory', false)
```

Метаданные — сообщение состоянию плагина удалить группу, а не непосредственное удаление
ресурса. Сам документ может совсем не измениться. Флаги lifetime.destroyed и view.isDestroyed
не позволяют отправлять запоздалые изменения в уничтоженное представление.

## 7. Общие индикаторы и загрузка файлов

`indicator.tsx` использует `ImageSkeletonDescriptor` из загрузки изображений и
`UploadLabel` из плагина загрузки CodeMirror. Визуальная часть уже переиспользуется.
DOM получает contentEditable=false, role=status и подпись name либо path.
WeakMap связывает DOM с RendererItem; destroyResourceIndicator удаляет этот элемент.

Нередактируемый DOM индикатора защищает его внутреннее содержимое. Он не запрещает
транзакции удалить окружающий фрагмент документа. За это отвечают фильтры движков.

Почему нельзя просто подключить плагин загрузки файла вместо замены:

- При загрузке бинарного файла окончательного адреса и узла ещё нет.
- PM [FilesBatchUploadProcess](./packages/editor/src/extensions/behavior/utils/upload.ts)
  добавляет декорацию и создаёт настоящий узел после ответа загрузчика.
- [WidgetDecorationPlugin](./packages/editor/src/extensions/behavior/WidgetDecoration/plugin.ts)
  перемещает виджеты по документу, но не содержит аналогичной защиты диапазонов фильтром.
- CM [FilesUploadPlugin](./packages/editor/src/markup/codemirror/files-upload-plugin/plugin.ts)
  для paste/drop сначала вставляет пробелы и виджеты, затем Markdown готового ресурса.
- При resourceReplacement исходный ресурс уже находится в документе, его нужно сохранить
  при ошибке и защитить от изменения на время ожидания.

У PM выбор файла через форму изображения/вложения также запускает соответствующий
upload process. Это не превращает загрузочный виджет в готовую защиту существующего узла.
Можно обобщать управление декорациями, но само переиспользование лоадера не решит
сбор ресурсов, глобальную замену и требования к истории.

## 8. CodeMirror: состояние, аннотации и эффекты

### 8.1. Сначала словарь

| Понятие | Что означает здесь |
| --- | --- |
| Transaction | Описание перехода между состояниями редактора |
| Annotation | Сведения о транзакции: например, это служебная замена или отслеженная вставка |
| StateEffect | Типизированное сообщение, которое может обработать состояние/расширение |
| StateField | Часть состояния редактора, обновляемая при транзакциях |
| Facet | Способ предоставить и собрать конфигурацию расширений |
| Decoration | Отображение поверх документа, не изменение его текста |

Аннотация или эффект сами не выполняют запрос и не удаляют диапазон.
Нужен код, который прочитает их и выполнит соответствующее действие.

### 8.2. options.ts и экспорты

Внутреннее расширение получает controller, resources, необязательный urls и shouldTrack.
`Pick<ResourceReplacementController, 'enabled' | 'busy' | 'start'>` ограничивает TypeScript-
интерфейс зависимости, а не создаёт новый объект и не удаляет методы во время выполнения.

`codemirror/index.ts` экспортирует реализацию и поддержку обработчиков для внутренних
импортов. Корневой `src/index.ts` предоставляет потребителю `codeMirrorResourceSupport`
и типы обработчиков; низкоуровневая функция codeMirrorResourceReplacement не становится
из-за внутреннего barrel-файла автоматически публичной функцией пакета.

### 8.3. tracked, resolved, release

```ts
type PendingRange = ResourceRange & {resource: ReplacementResource};
type Batch = {id: string; ranges: PendingRange[]};
const resolved = Annotation.define<boolean>();
const tracked = Annotation.define<Batch>();
const release = StateEffect.define<string>();
```

`tracked` содержит целую группу, а не один диапазон. `resolved` отмечает применение
ответа. `release` содержит id группы, которую нужно снять с отслеживания.

В отличие от PM, рядом с CM-диапазоном сохраняется извлечённый resource. В PM его
удобно перечитать у готового узла, а в CM для этого пришлось бы снова обращаться к
Markdown-дереву и обработчикам. Диапазон сам по себе содержит только позиции.
Сохранённый resource не выбирает глобальные замены: при ответе выполняется новый поиск.

### 8.4. transactionExtender и новые координаты

Extender исключает неинтересующие транзакции и вызывает collectInsertedMarkupResources.
Если вхождения есть, возвращает аннотации tracked и isolateHistory('full').
На этом этапе новый текст уже доступен как tr.newDoc, а iterChanges даёт координаты
добавлений в новом документе. Здесь и вычисляются диапазоны новой группы.

Поэтому pendingField.update не должен повторно перемещать новую trackedBatch:
её диапазоны уже относятся к результату текущей транзакции. Перемещать нужно старые группы.

### 8.5. pendingField.update

При обновлении поле удаляет группы, для которых есть release, перемещает старые диапазоны
и добавляет новую группу из tracked. При отсутствии интересующих изменений возвращает
прежний массив, чтобы не пересоздавать производные декорации без необходимости.

Для обычных изменений используются направления from:+1, to:-1: ввод на внешних
границах не должен становиться частью защищённого ресурса.
Для служебной замены используются from:-1, to:+1: диапазон должен сохранить заменённый
фрагмент, в том числе когда переписывание меняет его длину или достигает границы.

Аргумент направления mapPos определяет, к какой стороне изменения привязать граничную
позицию. Это не величина сдвига на один символ.

Через provide поле передаёт `batches.length > 0` в historyLocked.
Эта блокировка появляется уже при принятии вставки, до асинхронного ожидания контроллера.

### 8.6. Декорации, курсор и фильтр

Для каждого диапазона создаётся Decoration.replace с PendingWidget. Widget строит DOM
через общий createResourceIndicator и освобождает его при destroy.
Сравнение eq использует id виджета и ссылку на объект resource для переиспользования.

`decorationField` пересоздаёт DecorationSet, если изменился pendingField.
`EditorView.atomicRanges` сообщает навигации курсора, что декорации нужно обходить целиком.
Это не абсолютный запрет программно установить выделение внутрь диапазона.

Transaction filter разрешает resolved-замены, блокирует историю во время ожидания и
отклоняет текстовые изменения, пересекающие защищённые диапазоны. В CM документ текстовый,
поэтому здесь нет отдельной проверки изменения атрибутов узла, как у PM.

Стандартные команды истории CM создают транзакции с отключёнными фильтрами. Поэтому
одного transactionFilter недостаточно: lifetime-плагин дополнительно оборачивает dispatch
и проверяет готовые undo/redo-транзакции. В create.ts также учитывается historyLocked
для стандартных сочетаний клавиш. При destroy прежний dispatch восстанавливается,
если текущей обёрткой всё ещё владеет этот плагин.

### 8.7. updateListener

Только после принятого обновления listener читает tracked и вызывает controller.start.
WeakSet seen предотвращает повторную обработку того же объекта транзакции и не удерживает
его постоянно после освобождения остальными владельцами.

release-замыкание отправляет эффект удаления группы с addToHistory=false, если view жив.
apply-замыкание читает актуальный view.state и формирует замены всего текущего документа.
Подробный порядок dispatch описан в главе 12.

## 9. Грамматика и обработчики ресурсов

### 9.1. Два разных парсера

При преобразовании Markdown в документ ProseMirror используется markdown-it с
плагинами Diplodoc. CodeMirror получает своё дерево от Lezer. Поддержка конструкции
в одном парсере не означает автоматической поддержки в другом.

Обычное `![Схема](/a.png)` уже распознаётся стандартным Markdown-парсером CodeMirror.
Наш обработчик не разбирает эту строку регуляркой с нуля: он читает узлы Image и URL.
Для файлов YFM и размеров изображения нужны дополнительные правила.

### 9.2. Где теперь находится грамматика

После переноса yfmLang подключает:

```ts
extensions: [
    UnderlineExtension,
    MonospaceExtension,
    MarkedExtension,
    ImageSizeExtension,
    FileExtension,
]
```

`markdown-syntax.ts` содержит facet markdownSyntax и extendedMarkdownLanguage.
Пользовательские обработчики могут по-прежнему предоставлять собственные правила.
Для пути без явного базового языка defaultMarkdownLanguage тоже включает файлы и
размеры изображений. Если передан язык yfmLang, в нём эти правила уже есть.
Встроенные resource handlers теперь только читают дерево и повторно грамматику не подключают.

Почему это сложнее `mdInlineFactory({name: 'Marked', char: 61, tag: ...})`?
Фабрика парных маркеров использует общий механизм разделителей Lezer для конструкций
вида `==текст==`. У файла разные части: префикс, подпись, адрес, title или атрибуты.
Короткое подключение FileExtension не отменяет необходимость описать эти правила.

### 9.3. syntax-tree.ts

`completeResourceTree` берёт parser из language facet. Если полное дерево того же
документа уже доступно, используется syntaxTree(state). Если его нет или нужен новый
документ транзакции, вызывается parser.parse с DocumentInput.

DocumentInput адаптирует CodeMirror Text: сообщает длину, читает диапазон через
sliceString и отдаёт chunks до 4096 символов. Отдельного постоянного кэша дерева нет.

Нужно различать фоновую работу языковой поддержки CodeMirror и вызовы сборщика ресурсов.
Сам сборщик не требуется на каждое нажатие: он вызывается при подходящей вставке и
при применении ответа. Во время ожидания перемещаются сохранённые диапазоны.
Однако полное дерево может строиться заново в этих точках; точную стоимость без измерений
для конкретного документа оценить нельзя.

### 9.4. handlers.ts

Обработчик связывает настройку с синтаксическим деревом:

```ts
type CodeMirrorResourceHandler = {
    nodeType: string;
    urlAttribute: string;
    syntax?: MarkdownConfig;
    syntaxNodes: readonly string[];
    read(context: ResourceSyntaxContext): ResourceSyntaxMatch | undefined;
};
```

`nodeType` — ключ настройки resources, `syntaxNodes` — имена узлов дерева Lezer.
`read` получает node, doc, state, definitions и URL-кодек. Это чистое извлечение,
без dispatch и resolve. Во время транзакции текст нужно читать из doc, а не предполагать,
что state.doc уже содержит вставку.

codeMirrorResourceSupport возвращает массив из регистрации handler в facet и,
если есть handler.syntax, регистрации дополнительной грамматики.
Результат read содержит полный range, urlRange, attrs и при необходимости сведения
о ссылочном изображении. urlSyntax отличает буквальные файловые атрибуты от Markdown-адресов.

### 9.5. builtins.ts: обычное изображение

```text
![Схема](/a.png)

range:    [0, 16)
urlRange: [9, 15)
```

Image handler читает LinkMark/ResourceLabel для подписи и URL/ResourceURL для адреса.
urlRange убирает обрамляющие `<...>`, если они есть. imageLabel исключает Markdown-
разделители из подписи и декодирует экранирование и сущности.
Получаются `attrs: {src: '/a.png', alt: 'Схема'}`; категорию picture добавит сборщик по настройке.

Встроенное правило размеров имеет приоритет before: 'Image', но принимает только
конструкции, у которых действительно найден размер. Обычная картинка остаётся стандартному
парсеру. Передача собственного обработчика чтения не заменяет сам Markdown-парсер:
можно читать те же Image-узлы иначе без новой грамматики.

### 9.6. inline-destination.ts

Функция принимает контекст парсера, начало конструкции, длину префикса и allowSize.
Для `![` prefix равен 2, для `:file[` — 6. depth начинается с 1: открывающая скобка уже пройдена.

```ts
if (ch === 92) { i++; continue; } // пропуск экранированного символа
if (ch === 91) depth++;          // [
if (ch === 93 && --depth === 0) break; // ]
```

Счётчик нужен для вложенности: в `Отчёт [финальный]` первая закрывающая скобка ещё
не завершает внешнюю подпись. После неё требуется `(`.

Адрес разбирает готовый parseLinkDestination из markdown-it, title — parseLinkTitle.
Это уже переиспользование частей парсера, а не полностью ручной разбор URL.
Локальная позиция dest.pos переводится в позицию документа прибавлением start.

При allowSize читается суффикс вроде `=300x200`, затем проверяется финальная `)`.
Возвращаются labelEnd, urlStart, urlEnd, end и sized. Размер находится за пределами
urlRange; end указывает после закрывающей скобки, поскольку правая граница не включается.

### 9.7. file.ts и файловый handler

Поддерживаются формы:

```md
{% file src="/report.pdf" name="Отчёт" %}
:file[Отчёт](/report.pdf)
```

Для директивы используется inlineDestination. Для старой формы регулярка выделяет
конструкцию, затем цикл matchAll складывает диапазоны значений атрибутов в Map по имени.
Поэтому порядок src/name не важен. Кавычки в диапазоны значений не входят.
Дочерние элементы сортируются по from, чтобы дерево соответствовало порядку исходного текста.

File handler читает FileResourceURL и FileResourceName и возвращает attrs с href/download.
Имя атрибута в исходном `{% file src=... %}` не обязано совпадать с атрибутом узла `href`.
DirectiveSyntaxFacet ограничивает допустимые формы: disabled исключает директиву,
only исключает старую форму. Грамматическое распознавание и признание ресурсом — разные этапы.

<a id="resources"></a>
## 10. Сбор и замена Markdown-ресурсов

### 10.1. Выбор обработчика и проверки

collectMarkupResources выбирает первый подходящий handler по включённой настройке,
urlAttribute и имени синтаксического узла. Если выбранный handler.read вернул undefined,
следующий обработчик не вызывается. Это позволяет пользовательскому handler окончательно
отказаться считать конкретную конструкцию ресурсом.

Сборщик проверяет строковый адрес и допустимость URL, затем координаты:

```ts
Number.isInteger(from) && Number.isInteger(to)
    && from >= 0 && to >= from && to <= doc.length
```

Для обычного ресурса urlRange должен лежать внутри полного range.
Неподходящий адрес пропускается, а некорректные координаты вызывают ошибку контракта handler.
Это особенно важно для внешних расширений: неверный диапазон нельзя использовать для записи.

Из attrs сборщик читает поля, указанные в конфигурации, и создаёт:

```ts
{
    syntax: match,
    resource: {kind: description.kind, path, /* необязательное name */},
}
```

Включение kind в настройке меняет категорию ресурса, а не способ разбора Markdown.

### 10.2. Определения ссылок

Перед основным обходом собираются LinkReference из всего дерева. Кодовые ветки пропускаются.
Метка нормализуется, первое принятое определение сохраняется в definitions вместе
с диапазоном записи, диапазоном URL, адресом и title.

```md
![Схема][photo]
[Открыть][photo]

[photo]: /a.png "Описание"
```

У изображения range находится в первой строке, urlRange — в определении ниже.
Поэтому обычное требование вложенности диапазонов здесь неприменимо.
Проверяются definitionRange и labelTo — граница после `![Схема]`.

Для запуска resolve изображение и определение должны целиком входить в диапазоны
одной вставки. Они могут находиться в разных диапазонах. Если вставлено только
`![Схема][photo]`, а определение уже было в документе, запрос для него не запускается.
При глобальном применении ответа такого ограничения нет.

### 10.3. markupResourceChanges

Сначала проверяются и подготавливаются все новые адреса, даже без текущих совпадений.
Для каждого создаются literal и markdown формы; во второй `&` превращается в `&amp;`.
Старый файловый атрибут хранит URL буквально, Markdown декодирует сущности при чтении.

Далее вызывается collectMarkupResources без ranges: ответ ищет совпадения во всём
актуальном документе. Ключ — пара kind/path. Обычные ссылки и код не становятся целями
только из-за совпавшей подстроки адреса.

Обычный ресурс меняется только в urlRange:

```text
![Схема](/a.png =300x200)
                 ↓
![Схема](/copied.png =300x200)
```

У ссылочного изображения переписывается суффикс от labelTo до конца range:

```text
![Схема][photo] → ![Схема](/copied.png "Описание")
```

Общее определение `[photo]: /a.png "Описание"` не меняется: его может использовать
обычная ссылка. Title переносится в новую запись с экранированием специальных символов
числовыми HTML-сущностями.

Функция только собирает массив `{from, to, insert}`. Все координаты относятся к одному
state.doc. Разная длина новых адресов не требует сдвигать последующие позиции вручную:
изменения будут переданы CodeMirror вместе.

Подготовленный текст не проходит повторный поиск. Поэтому при `/a → /b` и `/b → /c`
исходный `/a` станет `/b`, а не `/c`. Если нужный текст уже стоит на месте, изменение
не добавляется. Пустой список изменений допустим.

<a id="urls"></a>
## 11. Подготовка адресов

ResourceLinkCodec содержит normalizeLink и validateLink. Реализация по умолчанию берётся
из `new MarkdownIt('zero')`. Само создание экземпляра не парсит документ: вызова parse нет.

validateResourceUrl сначала нормализует адрес, затем кодирует символы, которые могут
влиять на синтаксис: пробелы, угловые скобки, кавычки, круглые скобки и обратную косую черту.

```text
/report (final).pdf → /report%20%28final%29.pdf
```

encodeURIComponent оставляет некоторые символы незакодированными. Вложенная замена
вручную кодирует `'`, `(` и `)`. В её регулярке также есть `!`, но внешняя регулярка
не выбирает этот символ, поэтому отдельный восклицательный знак через неё не проходит.

Проверяются обе формы:

```ts
if (!urls.validateLink(path) || !urls.validateLink(encoded)) {
    throw new Error('Invalid resource URL');
}
return encoded;
```

Название функции не отражает всей работы: она и проверяет, и преобразует строку.
Это уместно для URL, но не должно автоматически применяться к непрозрачным id.
Предлагаемое обобщение value/oldValue/newValue описано в главе 14 и пока отделено
от зафиксированной здесь реализации path/oldPath/newPath.

<a id="history"></a>
## 12. Применение транзакции и граница истории

### 12.1. update ещё не dispatch

CodeMirror apply использует текущий view.state. Если edits пуст, он завершается без ошибки.
Если изменения есть, проверяет readOnly/editable и создаёт транзакцию:

```ts
let transaction = view.state.update({
    changes: edits,
    annotations: [resolved.of(true), Transaction.addToHistory.of(false)],
});
```

state.update создаёт транзакцию, но ещё не применяет её к EditorView.
resolved разрешает служебную замену защищённого ресурса и исключает новый resolve.
addToHistory=false не делает эту замену отдельным отменяемым действием.

Если после обработки нет docChanged, при непустых edits выбрасывается ошибка.
Это проверка наличия изменений в транзакции, а не буквальное сравнение двух строк.
Далее history.amend подготавливает эффекты корректировки истории; при необходимости
они добавляются к уже подготовленной транзакции с filter:false.

После dispatch сравниваются view.state.doc и transaction.newDoc. Подготовить изменения
недостаточно для успеха: фактический документ должен соответствовать ожидаемому.

### 12.2. Какая история требуется

```text
До вставки:     A(old)
После вставки:  A(old), B(old)
После resolve: A(new), B(new)
Undo вставки:  A(new)
Redo вставки:  A(new), B(new)
```

Повторного запроса на redo нет. Отмена вставки не откатывает глобальную замену у A.
При этом более старая история может восстановить старый URL — это допускает codex.md.
Обновление ресурсов, существующих только в истории, и постоянная таблица адресов не требуются.

Одного addToHistory=false недостаточно, чтобы выразить принадлежность изменений вставке.
CodeMirror-адаптер должен скорректировать обратные события, чтобы отмена удаляла
вставленный ресурс целиком и сохраняла внешние замены.

### 12.3. Что хранится в истории

В используемой реализации истории done содержит события для undo, undone — для redo.
У события в done поле changes описывает обратное изменение. Для вставленной картинки
это её удаление. При undo создаётся обратное событие для redo.

Наш HistoryEvent описывает только нужную часть внутренней структуры: changes, effects,
mapped и выделения. Адаптер зависит от этой структуры библиотеки; это сосредоточено
в history.ts, а не является универсальным контрактом любого редактора истории.

### 12.4. pasteEvent и invertedEffects

pasteEvent хранит массив диапазонов исходной вставки. Он **не хранит** соответствие
oldPath/newPath, имя ресурса или результат resolve.

```ts
pasteEvent.of([{from: 10, to: 30}])
```

invertedEffects получает транзакцию и возвращает эффекты, которые история сохранит
в событии её отмены. Для tracked-вставки здесь создаётся pasteEvent с диапазонами ресурсов.
Аннотация tracked сама по себе не становится постоянной исторической записью.

При undo/redo обработчик переносит pasteEvent в обратное событие через диапазоны
добавленного текста. При чистом удалении массив может быть пустым, но отметка сохраняется.
map эффекта описывает перенос его координат при отображении истории через изменения.
Повторный resolve исключается проверкой userEvent в extender.

### 12.5. Начало amend — изучено, но потребовало повторения

amend читает историю из tr.startState. Если её нет, возвращает пустой список эффектов.
После проверки ожидаемой структуры и наличия pasteEvent проходит done от новых событий
к старым: `history.done.length - 1`, затем index--.

Если сначала вставили картинку, а потом напечатали абзац, первым будет событие абзаца.
Рабочий doc и patch вычисляются локально; редактор во время цикла реально не откатывается.

owned собирает диапазоны pasteEvent и участки, которые обратное изменение события удаляет
без вставки нового текста. Последнее учитывает обычный ввод, добавивший ресурс во время запроса.

remaining содержит только замены за пределами owned. При обработке вставки B:

```text
patch:     замена A и замена B
owned:     диапазон B
remaining: замена A
```

Это не отказ применять замену к B. Это расчёт того, какие замены должны пережить отмену
вставки B: сама B исчезает, а A остаётся с новым адресом.

### 12.6. Отложенная часть

На этом пользователь попросил пропустить историю. Следующие темы пока не считаются
пройденными и требуют отдельного пошагового примера с документами и координатами:

1. ChangeSet и ChangeDesc, mapEvent и перенос между состояниями истории.
2. existing/event.mapped и перенос выделений.
3. Вычисление after из remaining.
4. Смысл `patch.invert(doc).compose(event.changes).compose(after)`.
5. Проход к более старому событию через изменение doc и patch.
6. Клонирование с сохранением прототипов вместо изменения существующих состояний.
7. Compartment, historyField.init и учёт addMapping при установке исправленной истории.

Этот учебник сохраняет пройденную часть, но не подменяет отложенный разбор краткой
формулой без объяснения.

<a id="example"></a>
## 13. Полный пример

До вставки документ содержит:

```md
![Первая](/a.png)
[Открыть файл](/a.png)
```

Пользователь вставляет:

```md
![Вторая](/a.png)
![Третья](/b.png)
```

При настройке image → kind: picture последовательность такая:

1. Интеграция фиксирует paste и разрешает обычной вставке продолжиться.
2. Транзакция добавляет Markdown или PM-узлы.
3. Сборщик находит только целиком вставленные ресурсы «Вторая» и «Третья».
4. Движок сохраняет их диапазоны, показывает лоадеры и защищает вхождения.
5. После принятого обновления вызывается controller.start.
6. Контроллер регистрирует операцию, уведомляет UI и вызывает resolve.

Приложение получает:

```ts
[
    {kind: 'picture', path: '/a.png', name: 'Вторая'},
    {kind: 'picture', path: '/b.png', name: 'Третья'},
]
```

Ответ может быть частичным:

```ts
{
    replacements: [
        {kind: 'picture', oldPath: '/a.png', newPath: '/copied/a.png'},
    ],
}
```

Контроллер проверяет ответ и вызывает apply. Адаптер ищет совпадения по всему текущему
документу и применяет изменения. Результат:

```md
![Первая](/copied/a.png)
[Открыть файл](/a.png)

![Вторая](/copied/a.png)
![Третья](/b.png)
```

Первая картинка не передавалась в запрос, но изменилась как текущее совпадение.
Обычная ссылка не изменилась. Для третьей картинки приложение не вернуло замену,
поэтому исходный адрес сохранился.

Контроллер завершает всю операцию статусом succeeded. Release снимает лоадеры и
защиту со всей группы, включая третью картинку. Если других операций нет, история
и переключение режима разблокируются.

При `{replacements: []}` операция также завершится успехом, только без изменения документа.
При ошибке результат не применяется, ресурсы сохраняют исходное содержимое, ожидание снимается.

<a id="design"></a>
## 14. Архитектурные вопросы из обсуждения

Этот раздел отделяет варианты развития от текущего поведения. Само обсуждение не означает,
что изменение уже реализовано или что соответствующий пункт codex.md отменён.

### 14.1. Можно ли назвать integration расширением или behavior

Да. CM-вариант технически возвращает Extension[], PM-вариант — расширение builder.
Integration подчёркивает связь DOM-событий с механизмом замены; extension — способ подключения.
Расположение в extensions/behavior возможно как отдельный рефакторинг.

В качестве аналогии обсуждалась структура GPT: есть
[MarkupGpt](./packages/editor/src/extensions/additional/GPT/MarkupGpt/index.ts) для CodeMirror
и [gptExtension](./packages/editor/src/extensions/additional/GPT/gptExtension/gptExtension.ts)
для ProseMirror, с общими интерфейсными частями выше по дереву.
Вынос интеграций в behavior был оставлен на будущее. Текущее расположение — tigger-policy.

### 14.2. Декларативные проверки

Разделять большие проверки на функции с предметными именами полезно, если имя объясняет
причину отказа: isHistoryTransaction, changesProtectedResources, isSelectionInCode.
PM-реализация уже получила такой рефакторинг: основные проверки находятся в utils.ts,
а extension.ts описывает последовательность действий.

Общий isHistoryTransaction для двух движков не устраняет различие протоколов:
в PM читается мета истории, в CM — userEvent. Отдельные функции с одинаковым смыслом
могут быть понятнее общей функции с ветвлением по типу движка.
Не нужно превращать каждый оператор в утилиту или строить DSL только ради отсутствия if.

### 14.3. Флаг pending в атрибуте узла вместо диапазона

В ProseMirror технически можно добавить атрибут вроде pendingOperationId и отображать
индикатор по нему. Но атрибут станет частью документа и потребует правил для истории,
сериализации, копирования, пользовательских узлов и снятия состояния.
Он сам по себе не запретит изменение или удаление узла: фильтр всё равно нужен.

Декорации и состояние плагина позволяют хранить ожидание вне документа. Возможны другие
формы хранения, например отображаемый DecorationSet, но это не означает автоматического
исчезновения необходимости сопровождать позиции.

### 14.4. Отказ от лоадеров и защиты

Обсуждалась схема: собрать ресурсы при вставке, запустить resolve, разрешить редактирование,
затем найти совпадения в текущем документе. Если пользователь удалил ресурс или изменил
его адрес, совпадения больше нет и замена к нему не применяется.

При таком решении могут уйти PendingWidget, decorationField, atomicRanges, сопровождение
защищённых диапазонов и проверки пересечений. Состояние незавершённых операций для
блокировки истории и режима останется. По состоянию CM-модуля на момент оценки это
предварительно означало сокращение примерно 80–110 строк, около 9–12% папки без тестов;
это оценка до реализации, а не измеренный результат рефакторинга.

Парсер, обработчики, сбор вставленных ресурсов, глобальный поиск, сериализация адресов
и история остаются. Новые сценарии редактирования/удаления ресурсов во время запроса
потребуют проверки корректности истории. Пользователь подтвердил, что требования к
undo/redo должны оставаться в границах codex.md, без полной нормализации старой истории.

Отказ от лоадеров и защиты в зафиксированном коде не сделан.

### 14.5. Можно ли вообще убрать поиск ресурсов

Нет, если требуется отличать изображения и файлы от обычных ссылок и кода.
Поиск нужен при подготовке запроса и при выборе мест применения ответа.
Убрать можно постоянное сопровождение защищённых вхождений, но это другая задача.
Замена всех подстрок одинакового URL нарушила бы границы ресурса и правила исключения кода.

### 14.6. Использовать PM-парсер в CodeMirror

Существующий MarkdownParser умеет получить узлы и их атрибуты с помощью markdown-it
и плагинов Diplodoc. Это могло бы убрать повторение правил распознавания YFM в Lezer.
Но готовый PM-документ не даёт точные координаты соответствующих URL в исходном Markdown.
Позиция PM-узла относится к структуре документа, а позиция CM — к тексту разметки.

Для лоадера, защиты, проверки принадлежности вставке и точечной замены нужны исходные
range/urlRange. Их пришлось бы сохранять во время токенизации и проводить через преобразования.
Обычные markdown-it tokens не предоставляют готовый диапазон каждого URL; стандартное
поле map описывает строки. Это требует отдельного механизма соответствия позиций.

Полностью преобразовать Markdown в PM, изменить атрибуты и сериализовать обратно возможно,
но сериализатор может изменить форму записи за пределами адресов. Для точечного изменения
исходного Markdown такой вариант имеет существенный недостаток.

Использование PM-парсера само по себе не требует парсить «на каждый чих».
Вызовы можно ограничить paste/drop и ответом resolve. Если позиции уже получены,
во время ожидания достаточно mapPos. Главное препятствие — получение исходных позиций,
а не обязательная частота вызовов.

### 14.7. Настройка только через внешние NodeSpec

Потребитель может настраивать NodeSpec через расширения, передаваемые в wysiwygConfig.
Поле `_resource` уже описано в типах проекта. Но сейчас EditorImpl явно выставляет его
из resources и очищает у остальных узлов. Поэтому просто добавить метаданные снаружи
и не передать resources недостаточно: они будут перезаписаны, а контроллер не создастся
по текущему условию.

Чтобы сделать NodeSpec источником истины, нужно изменить и сбор конфигурации, и условие
создания контроллера. Также нужно решить, откуда получит описания CodeMirror при ленивом
создании WYSIWYG. Варианты: общий реестр описаний на этапе настройки расширений или
построение схемы без view с принятием этой дополнительной зависимости.
Готовый NodeSpec не заменяет CM-handler: в нём нет правила чтения конкретной Markdown-записи.

Это обсуждаемое изменение, отдельно от обобщения URL-контракта ниже.

### 14.8. Ресурс может определяться id, а не URL

Предложен более общий контракт:

```ts
// Описание типа
{kind: 'asset', valueAttribute: 'assetId', nameAttribute: 'title'}

// Ресурс
{kind: 'asset', value: 'asset:ABC/123', name: 'Схема'}

// Ответ приложения
{
    replacements: [{
        kind: 'asset',
        oldValue: 'asset:ABC/123',
        newValue: 'asset:XYZ/456',
    }],
}
```

Такой переход меняет urlAttribute/path/oldPath/newPath на
valueAttribute/value/oldValue/newValue. Непрозрачное строковое значение нельзя по умолчанию
trim-ить, декодировать, менять регистр или пропускать через normalizeLink.

Нужно разделить три действия:

1. Проверить общий контракт ответа, принадлежность пары запросу и отсутствие конфликтов.
2. Проверить значение правилами конкретного типа ресурса. Для URL это могут быть правила ссылок;
   для id — другие правила или отсутствие дополнительной проверки.
3. Подготовить значение для конкретного места записи: атрибут PM или фрагмент синтаксиса CM.

Отказ от URL-нормализации для id не отменяет экранирование при записи в кавычки или
другую синтаксическую конструкцию. Также нельзя определять «это URL» по произвольной
категории kind: приложение может назвать изображение picture.

Для этого изменения подготовлен [отдельный промпт](./RESOURCE_REPLACEMENT_VALUE_PROMPT.md).
Оно не включает отказ от resources,
изменение лоадеров или новые гарантии истории. Главы выше описывают текущий URL-контракт;
после реализации обобщения их нужно будет обновить вместе с codex.md.

Для дальнейшего упорядочивания кода подготовлен
[промпт согласованного рефакторинга](./RESOURCE_REPLACEMENT_REFACTOR_PROMPT.md):
план и состав исходного коммита обсуждаются до изменений, затем создаётся точка возврата.

## 15. Вопросы для самопроверки с ответами

Сначала попробуйте ответить самостоятельно. В ответах исправлены ошибки, возникшие
во время обсуждения; они не воспроизводятся как верные утверждения.

<details>
<summary>1. Почему у узла image ресурс может иметь kind: picture?</summary>

image — ключ типа узла, picture — категория из настройки приложения. Категория не
определяет, как парсить Markdown, и не обязана совпадать с именем узла.
</details>

<details>
<summary>2. resolve и resources заданы, triggers пуст. Что произойдёт?</summary>

Контроллер может быть создан, но интеграции вставки не подключатся и paste/drop не
запустят обработку. Наличие контроллера само по себе не является обработчиком события.
</details>

<details>
<summary>3. Если убрать пользовательский onChange, перестанет ли блокироваться переключатель режима?</summary>

Нет. Интерфейс обновляется через внутренний onUpdate. Дополнительно сам changeEditorMode
проверяет занятость, потому что disabled-кнопка не предотвращает программный вызов.
</details>

<details>
<summary>4. Два вхождения имеют одинаковые kind/path, но разные имена. Сколько ресурсов уйдёт в resolve и что будет в лоадерах?</summary>

В одной операции уйдёт один ресурс с данными первого вхождения. Если у него нет имени,
имя второго не подставится. Лоадеры используют данные отдельных вхождений и могут
сохранить разные подписи. Повторная отдельная вставка запустит другую операцию.
</details>

<details>
<summary>5. Где находится start у PM-группы и зачем ставить его до controller.start?</summary>

view.update отправляет транзакцию с метаданными {type: 'start', id}. Состояние плагина
ставит started=true. Это предотвращает повторный запуск при синхронных вложенных обновлениях.
</details>

<details>
<summary>6. Что делает release, если документ не изменился?</summary>

Удаляет группу из состояния отслеживания, снимая её индикаторы и защиту. Это нужно
при пустом ответе, ошибке и отмене; удалять сам ресурс не требуется.
</details>

<details>
<summary>7. Почему DOM handler возвращает false, а filterTransaction может вернуть false?</summary>

В DOM handler false оставляет обработку события другим обработчикам. В filterTransaction
false отклоняет транзакцию. У одинакового boolean разные значения в разных API.
</details>

<details>
<summary>8. Зачем context и сравнение transferContext === context в микрозадаче?</summary>

context сохраняет объект конкретного события. Сравнение не даёт очистке старого события
стереть контекст нового. Blur тоже очищает краткоживущие сведения о событии.
</details>

<details>
<summary>9. Почему обработчик обновления CodeMirror не очищает контекст при изменении только выделения?</summary>

Такое обновление может быть промежуточным внутри обработки события и ещё не являться
вставкой текста. Очистка при docChanged оставляет контекст для вставки, а микрозадача
ограничивает его жизнь, если вставка не произошла.
</details>

<details>
<summary>10. Почему у drop нельзя использовать старое выделение как место вставки?</summary>

Позиция перетаскивания определяется мышью и может отличаться от курсора. Проверка
кода при окончательном сборе ресурсов всё равно выполняется по фактическому содержимому.
</details>

<details>
<summary>11. Почему в PM collectResourcesInRanges не объединяет одинаковые URL?</summary>

Его Map имеет ключ from и сохраняет отдельные вхождения для отдельных лоадеров и защиты.
Дедупликация запросов по kind/path выполняется позже контроллером.
</details>

<details>
<summary>12. Зачем PM сравнивает узлы, если уже проверил изменённые диапазоны?</summary>

Изменение атрибутов или марок может не дать обычного изменённого диапазона. Сравнение
узла до и после шага обнаруживает такую модификацию защищённого ресурса.
</details>

<details>
<summary>13. Что сохранится в Markdown во время ожидания?</summary>

Текущее содержимое с исходными адресами. Лоадер — декорация, не содержимое документа.
contentEditable=false у индикатора не заменяет фильтр защиты ресурса.
</details>

<details>
<summary>14. trackedBatch — один диапазон? Нужно ли ещё раз перемещать его в pendingField.update?</summary>

Это группа диапазонов. Extender уже вычислил их в новом документе, поэтому повторное
перемещение текущей транзакцией не требуется. Перемещаются ранее сохранённые группы.
</details>

<details>
<summary>15. atomicRanges полностью запрещает курсор внутри ресурса?</summary>

Нет. Оно направляет обычную навигацию; программная установка выделения возможна.
Защиту от изменений обеспечивает фильтр транзакций, а не только поведение курсора.
</details>

<details>
<summary>16. Чем range отличается от urlRange?</summary>

range — вся конструкция ресурса; urlRange — содержимое адреса. У ссылочного изображения
urlRange находится в общем определении вне range самого изображения.
</details>

<details>
<summary>17. Почему порядок src и name у {% file ... %} не важен?</summary>

Регулярка находит атрибуты, цикл сохраняет их диапазоны в Map по имени. Дальше src/name
читаются по ключам, а дочерние элементы дерева сортируются по исходной позиции.
</details>

<details>
<summary>18. Зачем inlineDestination считает вложенность скобок и входит ли размер в urlRange?</summary>

Внутренняя ] не должна закрывать внешнюю подпись; экранированные скобки также пропускаются.
Суффикс =300x200 расположен за пределами urlRange и сохраняется при замене адреса.
</details>

<details>
<summary>19. Первый подходящий handler вернул undefined. Запустится встроенный запасной обработчик?</summary>

Нет. Отказ выбранного handler окончателен для этого узла. Это позволяет переопределять
и положительное извлечение, и решение не считать конкретный узел ресурсом.
</details>

<details>
<summary>20. В существующее ![Схема]() вставили только /a.png. Запустится ли запрос для этой картинки?</summary>

collectInsertedMarkupResources не включит её: весь range изображения не помещается
в диапазон добавленного адреса.
</details>

<details>
<summary>21. Почему при ссылочном изображении нельзя просто заменить URL в определении?</summary>

На определение может ссылаться обычная ссылка. Поэтому изображение переводится
в inline-форму, а общее определение сохраняется.
</details>

<details>
<summary>22. Новые адреса длиннее старых. Нужно ли сдвигать следующие изменения в markupResourceChanges?</summary>

Нет. Функция ещё не меняет документ. Все изменения заданы в координатах одного state.doc
и применяются вместе. По этой же причине нет повторного прохода по новым адресам и каскада.
</details>

<details>
<summary>23. new MarkdownIt('zero') запускает разбор документа? Проверка адреса скачивает файл?</summary>

Нет и нет. Здесь извлекаются функции нормализации и проверки ссылки. Проверка
не устанавливает существование файла и может допускать относительный путь.
</details>

<details>
<summary>24. Что меняет state.update и что меняет dispatch?</summary>

state.update создаёт транзакцию с новым состоянием, не обновляя EditorView.
dispatch отправляет её редактору. После него адаптер проверяет ожидаемый документ.
</details>

<details>
<summary>25. Достаточно shouldTrack=true или регистрации handler для вызова resolve?</summary>

Нет. Ещё нужны включённая обработка, подходящая транзакция, включённый тип и фактически
найденные вставленные ресурсы. Регистрация handler только обучает извлечению данных.
</details>

<details>
<summary>26. Что хранит pasteEvent: удаление картинки или карту URL?</summary>

Ни то ни другое: он хранит диапазоны, относящиеся к вставке. Удаление хранится в changes
события undo, а замены адресов передаются в amend через транзакцию. Сам pasteEvent
не позволяет узнать новый адрес.
</details>

<details>
<summary>27. После картинки напечатали абзац. Какое событие amend обходит первым?</summary>

Абзац: цикл идёт от последнего события done к первому.
</details>

<details>
<summary>28. A и C существовали, B вставили. Ответ меняет все три. Что в remaining при обработке вставки B?</summary>

Замены у A и C. B принадлежит отменяемой вставке и удалится целиком. В текущем документе
ответ всё равно применяется ко всем трём; remaining нужен для вычисления будущего undo.
</details>

<details>
<summary>29. Почему старая картинка изменилась, хотя её не передавали в resolve?</summary>

Запрос составляется из вставки, а ответ применяется ко всем текущим совпадениям пары
kind/path. Область запроса и область применения намеренно различаются.
</details>

<details>
<summary>30. Что происходит при пустом или частичном ответе?</summary>

Вся операция завершается успехом. Ресурсы без замены сохраняют адреса, но их лоадеры
и блокировки снимаются вместе с остальной группой.
</details>

| --- | --- |
| Ресурс | Типизированное значение, в текущем контракте kind/path |

Если реализуется переход к id/value, обновить главы 1, 3, 4, 6, 8–11 и примеры ответа.
