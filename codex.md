# Замена ресурсов: согласованные решения

Решения по первой версии, согласованные 21 сентября 2026 года.

## Назначение

При копировании содержимого из документа A в документ B приложение может скопировать ресурсы и вернуть новые адреса. Копирование из документа A в тот же документ A тоже может приводить к замене. Решение о необходимости копирования принимает приложение в `resolve`.

Загрузка файлов из файловой системы — отдельный механизм. Замена ресурсов работает с уже готовыми ссылками.

## Конфигурация и расширения

- Настройки передаются через `resourceReplacement` в конфигурации `useMarkdownEditor`.
- Потребитель явно указывает обрабатываемые ресурсы в `resourceReplacement.resources`. Без настройки обработка выключена.
- Описание узла остаётся в конфигурации замены: `kind`, `valueAttribute`, необязательный `nameAttribute` и `valueType: 'url'` для пользовательских URL.
- Поддерживаются картинки, файловые вложения и произвольные типы из расширений.
- Для пользовательского типа требуется поддержка обоих режимов: WYSIWYG и Markdown. Обработчик синтаксиса Markdown подключается через расширение.
- Обычные текстовые ссылки сами по себе не считаются ресурсами.

## Запуск и область замены

- Поддерживаемые триггеры — `paste` и `drop`.
- Shift при вставке не исключает обработку: если в результате вставки появился поддерживаемый ресурс, он обрабатывается.
- Блоки кода и строчный код исключаются как при сборе ресурсов, так и при применении результата `resolve`. Совпадающие адреса внутри кода не заменяются.
- Загрузка документа и обычные программные изменения сами по себе не запускают замену.
- Ресурсы одной вставки передаются в один общий `resolve`, включая разные типы. Повторы объединяются по паре «тип ресурса + исходный адрес».
- Результат применяется ко всем совпадениям этой пары в текущем документе, а не только к вставленному фрагменту.
- Например, если в документе уже была картинка `old.png` и вставили ещё одну `old.png`, результат `old.png → new.png` обновляет обе.

## Параллельные операции

- Новая вставка может запускать отдельный `resolve`, пока предыдущий запрос ещё выполняется.
- Для первой версии допускается текущая модель конкуренции: если два запроса заменяют один исходный адрес разными адресами, первый применённый результат может убрать совпадения для второго.
- Дополнительную координацию таких запросов в первой версии не вводим.

## Ожидание и сохранение

- Пока выполняется запрос, вставленные ресурсы показываются с лоадерами и защищены от редактирования и удаления.
- Остальной документ можно редактировать, включая ранее существовавшие ресурсы с теми же адресами.
- Undo/redo и переключение между Markdown и WYSIWYG заблокированы на время незавершённых операций.
- Исходные адреса уже находятся в документе во время ожидания; лоадеры являются визуальным представлением.
- Приложению предоставляется признак наличия незавершённых операций. Разрешать ли сохранение в этот момент, решает приложение. Сохранение во время ожидания может записать исходные адреса.

## Результат, ошибки и таймаут

- Частичный результат допустим: `resolve` может вернуть замены только для части переданных ресурсов или пустой список.
- Ресурсы без замены сохраняют исходные адреса. Валидный частичный или пустой результат считается успешным завершением всей операции.
- При ошибке `resolve` или отмене операции исходные адреса сохраняются, блокировки и лоадеры снимаются.
- Повторная попытка не нужна.
- Таймаут необязателен: если потребитель не задал `timeoutMs`, ограничения времени ожидания нет.
- Если `timeoutMs` задан, он должен быть конечным положительным числом. По истечении времени операция завершается как ошибка; блокировки и лоадеры снимаются, исходные адреса сохраняются.
- Поздний результат завершённой или отменённой операции игнорируется.

## Публичное управление операциями

Сохраняем возможность отменять конкретный запрос из приложения:

- `getPendingResourceReplacements()` возвращает незавершённые операции с `operationId`; непустой список означает наличие незавершённой обработки.
- `cancelResourceReplacement(operationId)` отменяет выбранную операцию, не затрагивая остальные.
- `onChange` сообщает статусы `pending`, `succeeded`, `failed`, `cancelled`.
- `resolve` получает контекст с `operationId` и `AbortSignal`.
- При уничтожении редактора незавершённые операции отменяются.

## История изменений: границы первой версии

- Undo/redo самой вставки должны сохранять новые адреса: повторное выполнение вставки не должно возвращать исходные адреса или повторять запрос.
- Отмена вставки не должна откатывать замену адреса у ресурса, который уже был в документе.
- При откате более ранних изменений допускается восстановление старых адресов. Например, undo изменения подписи или размера может восстановить сохранённый в истории узел со старым адресом.
- Не требуется обновлять ресурсы, существующие только в истории, включая ранее удалённые ресурсы.
- Таблицу соответствий адресов для всей истории не добавляем. Полную нормализацию старой истории откладываем, чтобы не усложнять первую версию.

## Состояние реализации после обсуждения

Большая часть согласованного поведения уже была реализована. По итогам обсуждения внесены два изменения:

1. Убран пропуск paste с Shift в обоих режимах.
2. Убран таймаут по умолчанию в две минуты; таймер создаётся только при явно заданном `timeoutMs`.

Добавлены регрессионные проверки. В контейнере прошли 167 тестов в пяти выбранных наборах и проверка TypeScript. ESLint завершился без ошибок, с предупреждениями в существовавшем коде.

Поддержка пользовательского типа в соответствующем режиме проверяется по мере использования. Проверка обоих режимов заранее при инициализации не добавлялась.

## Обобщение строкового значения ресурса

- `resources` остаётся источником конфигурации, в том числе для непрозрачных id.
- Запрос: `{kind, value, name?}`. Ответ: `{replacements: [{kind, oldValue, newValue}]}`.
- Значение — только строка; подпись `name` необязательна. Ключ дедупликации и замены —
  точная пара `(kind, value)`, без trim, смены регистра и URL-преобразований id.
- Прежние упоминания адресов выше относятся также к непрозрачным значениям ресурсов.
- Встроенные image/src и FILE_TOKEN/href сохраняют URL-правила независимо от `kind`.
  Пользовательские URL явно помечаются `valueType: 'url'`; остальные значения непрозрачны.
- В CodeMirror `valueRange` задаёт заменяемый текст, а обязательный `serialize(value)`
  результата обработчика отвечает за безопасную запись в конкретный синтаксис.
- В ProseMirror подготовленное значение записывается в `valueAttribute`.
- Весь ответ проверяется и все изменения подготавливаются до dispatch. Ошибка
  сериализации или URL-проверки не приводит к частичному применению.
- Совместимость со старыми именами контракта не добавляется.
