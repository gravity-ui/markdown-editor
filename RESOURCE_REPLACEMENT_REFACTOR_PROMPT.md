# Промпт: согласованный рефакторинг resourceReplacement

Нужно проанализировать модуль resourceReplacement и сделать его код более декларативным
и понятным. Сначала согласуй со мной изменения. До начала рефакторинга нужно сделать
коммит текущего состояния, чтобы была отдельная точка возврата.

Прочитай AGENTS.md, codex.md и RESOURCE_REPLACEMENT_TUTORIAL.md. Тесты не запускай.
В проекте могут параллельно выполняться другие изменения, поэтому исходи из текущего
содержимого файлов, а не из предположений об их прежнем расположении.

## Порядок работы — обязателен

1. Сначала выполни только чтение и анализ. Посмотри состояние репозитория, существующие
   незакоммиченные изменения и актуальную архитектуру.
2. Подготовь конкретный план для согласования. Для каждого предложения укажи:
   - файл и функцию;
   - что сейчас затрудняет понимание;
   - предлагаемое имя, разделение или расположение;
   - короткий пример структуры до/после;
   - затрагивает ли предложение публичный API или поведение.
3. Отдельно покажи состав исходного коммита: какие текущие изменения предлагаешь сохранить
   и каким сообщением. Не включай вслепую все файлы через git add . и не добавляй
   несвязанные изменения без согласования. Если без них исходное состояние неполно,
   объясни зависимость. Ничего не откатывай и не прячь в stash самовольно.
4. Дождись моего явного согласования плана и состава коммита. До этого не меняй исходники
   и не создавай коммит.
5. После согласования сначала создай коммит исходного состояния. Если затронутые файлы
   изменились с момента согласования, покажи разницу и уточни состав. При чистом состоянии
   зафиксируй текущий commit hash как точку отсчёта, не создавая пустой коммит.
6. Только затем выполняй согласованный рефакторинг. Согласованный пакет изменений не
   требует повторного разрешения для каждой строки. Новые идеи, выходящие за пакет,
   сначала предложи и дождись согласования.
7. В конце покажи результат и выполненные проверки. Финальный коммит рефакторинга и push
   не делай без отдельного указания. Тесты не запускай.

## Цель рефакторинга

Основные функции должны читаться как последовательность действий предметной области:
проверить источник транзакции, проверить ограничения, собрать ресурсы, обновить группы,
подготовить замены, применить результат, снять ожидание.

Например, в основном потоке лучше видеть:

```ts
if (isHistoryTransaction(tr) && isReplacementPending(state)) return false;
if (changesProtectedResources(tr, state, batches)) return false;
```

чем длинные вложенные условия, смешанные с обходом шагов и пересчётом координат.
Названия здесь иллюстрируют цель; конкретный API предложи после чтения кода.

## Одинаковое назначение — понятные одинаковые имена

В CodeMirror и ProseMirror можно иметь отдельные реализации функции с одним названием:

```ts
// В модуле CodeMirror
function isHistoryTransaction(tr: CodeMirrorTransaction) { /* ... */ }

// В модуле ProseMirror
function isHistoryTransaction(tr: ProseMirrorTransaction) { /* ... */ }
```

Это подчёркивает одинаковое назначение и сохраняет специфичный для движка способ проверки.
Не нужно ради этого создавать общий union-тип транзакции, instanceof-разветвления или
универсальный адаптер. Проверь другие операции, для которых такое согласование имён полезно:
определение исходного локального изменения, проверка кода, сбор вставленных ресурсов,
защита вхождений, применение результата и освобождение группы.

Если смысл или существенные гарантии функций различаются, не маскируй это одинаковым
названием. Предложи общий принцип именования с явными уточнениями.

## Правильное расположение ответственности

Во время изучения обнаружилось, что правила Markdown-грамматики находились в модуле
замены ресурсов, хотя относятся к языковой поддержке CodeMirror. Их уже переносили в
packages/editor/src/markup/codemirror/syntax и подключали через yfm.ts/markdown-syntax.ts.
Проверь текущее состояние: не повторяй перенос, если он завершён.

Ищи аналогичные случаи:

- код общей грамматики внутри бизнес-функции;
- универсальная работа с декорациями или представлением, необоснованно привязанная
  к конкретной операции;
- дублирование правил между слоями;
- циклические или обратные зависимости;
- общие проверки, смешанные с API конкретного движка.

Каждый такой перенос сначала предложи с объяснением ответственности и зависимостей.
Не переноси код только из-за общего слова в названии и не создавай новый общий модуль,
если это ухудшает локальность или у него нет понятного назначения.

## Как извлекать функции

- Название должно объяснять действие или условие, а не скрывать их за handle/process/check.
- Входы и результат должны быть явными; по возможности отделяй вычисления от dispatch
  и других побочных эффектов.
- Оставляй рядом стадии одного алгоритма, если разнесение заставляет прыгать по файлам.
- Нормальные циклы допустимы внутри небольшой именованной операции. Не заменяй каждый for
  на цепочку reduce/map и не делай обёртку ради каждой строки.
- Не выноси состояние замыкания так, чтобы переприсваивание параметра перестало менять
  нужную внешнюю переменную. Это особенно важно для captureSource и transferContext.
- Границы координат, порядок шагов, правила mapPos и владение диапазонами должны остаться
  понятны. Короткий комментарий с причиной полезнее общего имени, скрывающего сложность.
- Если history.ts требует большой самостоятельной переделки, выдели её в отдельный
  согласуемый пункт, а не смешивай с механическим упорядочиванием остальных файлов.

## Что сохранить

Сохрани действующий контракт codex.md: условия запуска, дедупликацию, область глобальной
замены, исключение кода и обычных ссылок, обработку ссылочных изображений, лоадеры,
защиту, блокировки, границы истории, отмену, таймауты, пустые и частичные ответы,
отсутствие каскада и игнорирование поздних результатов.

Проверяй сохранение порядка действий: например, PM start должен помечаться до вызова
контроллера, запросы запускаются после принятого обновления, а состояние снимается
при завершении даже без изменения документа.

Не меняй публичный API, не удаляй лоадеры, не вводи настройку только через NodeSpec
и не объединяй сюда переход URL → value/id без отдельного согласования.
Если такой переход уже реализуется в другом чате, учитывай актуальные имена и не
возвращай старый контракт. Не перезаписывай чужие изменения.

Документацию к согласованным изменениям пока пиши на русском. Поддерживай актуальность
учебного разбора, но согласуй его обновление, если файл параллельно редактируется.

Первый ответ должен содержать результаты чтения, предложения для согласования и состав
исходного коммита. Не начинай рефакторинг до моего ответа.
