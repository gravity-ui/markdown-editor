# Сбор и замена ресурсов в CodeMirror

Разбор [resources.ts](./resources.ts). Согласованное поведение всей функции замены
описано в [codex.md](../../../../../../codex.md).

## Два момента поиска

1. После вставки `collectInsertedMarkupResources` собирает ресурсы, целиком попавшие
   в добавленные диапазоны. Их данные нужны для запроса `resolve`.
2. После ответа `resolve` функция `markupResourceChanges` ищет совпадения во всём
   текущем документе и подготавливает точечные изменения значений.

Диапазоны исходной вставки не ограничивают область применения результата. Например,
если до вставки уже была картинка `/a.png`, а затем вставили ещё одну такую же,
ответ `/a.png → /copied.png` должен обновить обе.

Это поиск по синтаксическому дереву, а не замена всех совпавших подстрок. Обычная
ссылка с тем же адресом не является ресурсом сама по себе. Ветки `FencedCode`,
`CodeBlock`, `InlineCode` и `Monospace` исключаются из обхода вместе с потомками.

## Как выбираются документ и область поиска

`collectMarkupResources(state, options, tr?, ranges?)` использует `tr.newDoc`,
если передана транзакция, иначе — `state.doc`. При переданной транзакции `state`
может быть старым состоянием: настройки читаются из него, но текст и позиции —
из нового документа.

`completeResourceTree` из [syntax-tree.ts](./syntax-tree.ts) возвращает полное дерево
нужного документа. Если переданы `ranges`, обход ограничивается ими; без `ranges`
обрабатывается весь документ. Пустой массив диапазонов означает отсутствие работы.

`collectInsertedMarkupResources` получает координаты добавленного текста из
`tr.changes.iterChanges`. Используются координаты в новом документе. Одна транзакция
может содержать несколько раздельных изменений, поэтому диапазонов может быть несколько.

Ресурс должен целиком помещаться в один из этих диапазонов. Если в существующее
`![Схема]()` вставить только `/a.png`, целое изображение не будет считаться вставленным
ресурсом: добавился лишь адрес внутри уже существующей конструкции.

## От синтаксического узла к данным ресурса

Обработчики из [handlers.ts](./handlers.ts) связывают синтаксические узлы CodeMirror
с ключами настройки `resources`. Сборщик проверяет наличие обработчика для каждого
включённого типа и совпадение его `valueAttribute` с настройкой.

Для очередного узла выбирается первый обработчик, у которого:

- включена настройка `resources[handler.nodeType]`;
- совпадает `valueAttribute`;
- `syntaxNodes` содержит имя текущего узла дерева.

После выбора вызывается `handler.read`. Если он вернул `undefined`, узел пропускается:
перехода к следующему обработчику нет. Пользовательский обработчик может таким образом
не только изменить извлечение данных, но и отказаться считать конструкцию ресурсом.

Например, для `![Схема](/a.png)` обработчик возвращает:

```ts
{
    range: {from: 0, to: 16},
    valueRange: {from: 9, to: 15},
    attrs: {src: '/a.png', alt: 'Схема'},
    serialize: (value) => value.replace(/&/g, '&amp;'),
}
```

При настройке `{kind: 'picture', valueAttribute: 'src', nameAttribute: 'alt'}` сборщик
создаёт `{kind: 'picture', value: '/a.png', name: 'Схема'}`. Категория `kind` берётся
из настройки, а не из имени синтаксического узла. Необязательное имя включается
только тогда, когда соответствующий атрибут содержит непустую строку.

Результат сборщика содержит обе части: `syntax` с координатами и формой записи,
а также `resource` с данными для сопоставления и запроса. Сборщик сохраняет отдельные
вхождения; объединение одинаковых ресурсов для `resolve` выполняет контроллер.

## Проверки результата обработчика

Значение должно быть строкой. Только URL-ресурсы проходят `urls.validateLink`:
встроенные image/src и FILE_TOKEN/href, а также пользовательские ресурсы с
`valueType: 'url'`. `kind` не определяет семантику значения. Непрозрачный id
сопоставляется точно: без trim, смены регистра, URL-нормализации и декодирования.
Обработчик обязан вернуть чистую функцию `serialize(value)` для своего синтаксиса.

Диапазоны должны иметь целые координаты и удовлетворять
`0 <= from <= to <= doc.length`. Правая граница не включается в диапазон.
Для обычного ресурса `valueRange` должен находиться внутри `range`.
Некорректные координаты вызывают ошибку контракта обработчика, а не используются
для изменения произвольного участка документа.

## Ссылочные изображения

```md
![Схема][photo]

[photo]: /a.png "Описание"
```

Перед сбором ресурсов функция отдельно собирает определения ссылок из всего дерева
в `definitions`. Метки нормализуются; при повторении метки сохраняется первое
принятое определение. Определение содержит адрес, его диапазон, диапазон всей записи
и необязательный `title`.

У ссылочного изображения `range` охватывает `![Схема][photo]`, а `valueRange` находится
в определении ниже. Поэтому здесь нет требования вложенности `valueRange` в `range`.
Дополнительно проверяются `definitionRange` и позиция `labelTo` — граница после
`![Схема]`, с которой начинается заменяемый суффикс.

При сборе вставленных ресурсов и изображение, и его определение должны целиком
входить в диапазоны одной транзакции. Они могут находиться в разных диапазонах.
Вставка только `![Схема][photo]` со ссылкой на старое определение не запускает запрос
для этого изображения. При применении ответа ко всему документу такого ограничения нет.

## Как подготавливаются замены

`markupResourceChanges` принимает карту замен. Ключ создаётся через `resourceKey`
из пары `(kind, oldValue)`, значение содержит новый адрес.

Сборщик обходит текущие ресурсы и ищет замены по точной паре `(kind, value)`.
Для совпавших URL-ресурсов [validateResourceUrl](../urls.ts) проверяет исходное и
подготовленное значения, нормализует URL и кодирует опасные для адреса символы.
Непрозрачные id пропускают этот шаг. URL-пары исходной вставки сохраняются на время
запроса, чтобы проверить их ответ даже при исчезновении всех текущих совпадений.

Затем `syntax.serialize(value)` готовит текст для конкретного `valueRange`.
Встроенные Markdown-адреса экранируют `&` как `&amp;`, старые файловые атрибуты
хранят URL буквально. Пользовательский обработчик сам сериализует id, например
через `JSON.stringify` для JSON-строки в кавычках. Если диапазон включает кавычки,
сериализатор возвращает их тоже. Результат повторного разбора должен сохранять id
в точности. При невозможности представить значение сериализатор бросает ошибку.

Все проверки и сериализация завершаются до dispatch. Ошибка даже у последнего
вхождения не приводит к частичному изменению документа.

У обычного ресурса изменяется только `valueRange`. Например:

```md
![Схема](/a.png =300x200)
```

превращается в `![Схема](/copied.png =300x200)`: подпись, размер и окружающий текст
не переписываются.

У ссылочного изображения заменяется суффикс от `labelTo` до конца `range`:
`![Схема][photo]` превращается в `![Схема](/copied.png "Описание")`.
Общее определение `[photo]: /a.png "Описание"` остаётся прежним, поскольку на него
могут ссылаться обычные ссылки. `title` переносится в новую запись, а его специальные
символы экранируются числовыми HTML-сущностями.

## Почему не нужно сдвигать позиции следующих замен

Функция не изменяет документ во время обхода. Она возвращает массив
`{from, to, insert}`, где все координаты относятся к одному исходному `state.doc`.
Вызывающий код в [extension.ts](./extension.ts) передаёт изменения одной транзакцией
CodeMirror. Разница в длине старых и новых адресов учитывается при её применении;
вручную пересчитывать координаты следующих изменений не нужно.

По той же причине нет каскадной замены в рамках одного ответа. Для правил
`/a.png → /b.png` и `/b.png → /c.png` исходное изображение `/a.png` станет `/b.png`,
а исходное `/b.png` — `/c.png`. Подготовленный новый текст повторно не обходится.

Если заменяемый текст уже совпадает с подготовленным, изменение не добавляется.
Пустой массив изменений означает, что переписывать документ не требуется.
Работа с историей выполняется отдельно вызывающим кодом и [history.ts](./history.ts).
